00 Premessa — cosa valuta davvero un recruiter

Un repository Power BI non è una raccolta di file .pbix. È un sistema di comunicazione: deve rispondere a tre domande entro 90 secondi — sai modellare i dati?, sai scrivere DAX corretto?, sai comunicare insight?

Nota sul .pbix: GitHub non esegue file binari Power BI. Il .pbix va sempre accompagnato da screenshot, export PDF e documentazione testuale del modello. Senza questi, il file è opaco a chiunque lo visiti senza aprire Power BI Desktop.

Il profilo Data & BI Analyst richiede di dimostrare competenze su tre livelli distinti: dati (modello, trasformazioni), analisi (DAX, logica di business) e presentazione (layout, storytelling visivo, pubblicazione su Service).

02 File obbligatori

La loro assenza è un segnale negativo immediato per chiunque visiti il repo.

README.md (root)
Indice dei progetti, stack tecnologico, link ai singoli report. Prima pagina che legge chiunque visiti il repo.
obbligatorio
*.pbix
File Power BI principale. Deve contenere modello pulito, misure documentate, almeno 2–3 pagine report con layout curato.
obbligatorio
model_schema.png
Screenshot della vista modello in Desktop. Dimostra la capacità di progettare star schema o snowflake corretti.
obbligatorio
dax_measures.md
Documentazione di ogni misura DAX: nome, formula, contesto di utilizzo. Dimostra comprensione del filter context.
obbligatorio
README.md (progetto)
Contesto di business, domande analitiche affrontate, fonte dati, screenshot principali, limitazioni note.
obbligatorio
.gitignore
Esclude file di sistema, cache locali, dati sensibili. Segnale di professionalità anche in un portfolio personale.
obbligatorio

Attenzione: evita dataset generici come iris o titanic per Power BI. I recruiter BI cercano modelli con almeno 3–4 tabelle, relazioni non banali e metriche riconoscibili (vendite, margini, KPI HR). Un'analisi del Titanic in Power BI non dimostra competenze di business intelligence applicata.

06 README efficace — struttura minima per progetto

Ogni cartella-progetto deve avere un README che risponde a queste domande nell'ordine:

# Nome progetto — Sottotitolo descrittivo

## Contesto di business
2–3 righe: chi sono i destinatari, quale problema risolve il report.

## Domande analitiche
Bullet: 3–5 domande concrete cui il report risponde.

## Modello dati
![Schema modello](docs/model_schema.png)
Tabelle, relazioni, cardinalità, tipo (star / snowflake).

## Misure DAX principali
Tabella: nome | formula breve | scopo

## Screenshot
![Overview](screenshots/overview_page.png)

## Stack
Power BI Desktop 2.x, dataset fonte, Power Query M.

## Link report live    ← se disponibile su Service
## Note e limitazioni

✔ Cosa include un buon README

  • Business context esplicito
  • Screenshot inline visibili su GitHub
  • Tabella misure DAX leggibile
  • Limitazioni dichiarate onestamente
  • Link al report live o al PDF export

✘ Errori comuni

  • README vuoto o con solo il titolo
  • Nessuno screenshot (il .pbix è opaco)
  • DAX non documentato
  • Dataset non incluso né linkato
  • Nessun contesto di business

07 Power BI Service — come documentarlo su GitHub

Power BI Service non è un file, ma puoi dimostrarne l'uso in modo convincente. Tre opzioni pratiche, dalla più semplice alla più efficace.

A
Link al report pubblico. Pubblica il report su un workspace personale con dataset pubblico, imposta Share → Anyone with the link e inserisci il link nel README. Richiede licenza Pro o tenant Developer (gratuito per sviluppatori Microsoft).
B
Screenshot del Service. Screenshot di: workspace organizzato, scheduled refresh configurato, dashboard costruita con pin da report, RLS verificata con View as role. Inseriscili in docs/service_screenshots/ con un service_setup.md.
C
Embed su GitHub Pages. Crea embedded_demo/index.html con l'iframe embed di Power BI Service. Attiva GitHub Pages: il report diventa visitabile da browser senza Power BI installato. Massima visibilità, zero attrito per il visitatore. 
/* Esempio iframe embed — File → Embed report → Website or portal */

<iframe
  width="100%"
  height="600"
  src="https://app.powerbi.com/view?r=TOKEN_PUBBLICO"
  frameborder="0"
  allowFullScreen="true"
></iframe>
Cosa dimostra: pubblicare su Service — workspace, dataset refresh, condivisione — è una competenza operativa distinta da Desktop. Documentarla anche solo con screenshot vale molto in un colloquio tecnico su profili BI aziendali.

08 Checklist finale prima di pubblicare

Struttura e contenuto

  • ▸ README root con indice progetti e stack tecnologico
  • ▸ Almeno 2 progetti completi con struttura standardizzata
  • ▸ Ogni progetto ha: .pbix, README, schema modello, misure DAX documentate
  • ▸ Dataset inclusi nel repo o linkati con fonte attendibile
  • ▸ Screenshot inline visibili su GitHub (non solo link)
  • ▸ Export PDF di almeno un report

Qualità tecnica dimostrabile

  • ▸ Star schema corretto con chiavi surrogate o naturali documentate
  • ▸ Misure DAX con almeno: YTD, comparativo anno precedente, % su totale
  • ▸ Power Query: almeno un merge, una trasformazione non banale documentata
  • ▸ RLS configurata e documentata in almeno un progetto
  • ▸ Tema personalizzato applicato (.json nel repo)

Power BI Service

  • ▸ Almeno un report pubblicato su workspace (anche Developer license)
  • ▸ Screenshot del workspace e del refresh schedulato
  • ▸ Link diretto o embed live nel README

Hygiene del repository

  • ▸ .gitignore configurato (esclude .DS_Store, Thumbs.db, cache locali)
  • ▸ Nessun dato sensibile o credenziale committata
  • ▸ Nomi file coerenti e leggibili (snake_case, nessun "report1.pbix")
  • ▸ Commit history con messaggi descrittivi
// opinione critica — basata su evidenza

Il problema più comune nei portfolio Power BI è la confusione tra avere i file e dimostrare competenza. Un .pbix non documentato è un binario opaco: GitHub non lo renderizza, il recruiter non lo apre, il dato non parla da solo.

Il vero differenziale, nel 2025–2026, non è la quantità di report ma la capacità di costruire un modello dati corretto, documentare le scelte DAX e rendere visibile il risultato senza richiedere software installato. Un singolo progetto con schema visibile, misure documentate e report live su Service vale strutturalmente più di dieci .pbix senza contesto.

Per il profilo Data & BI Analyst il punto di partenza concreto è: due progetti completi su AdventureWorks e un dataset a scelta, più una pagina GitHub Pages con embed. Tre settimane di lavoro organizzato producono un portfolio superiore alla media del mercato italiano su questa figura professionale.
